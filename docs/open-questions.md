## API のトークンをアクセストークンに変えるか

`architecture.md`「認証」では、API Gateway の JWT Authorizer へ渡すトークンを ID トークンとしている。Cognito のアクセストークンには `email` クレームが入らず、そのためだけに Cognito への呼び出しと権限を増やすのは割に合わない、という判断だった。

一般には、API の認可にはアクセストークンを使い、route ごとに scope を要求する構成が推奨される。将来、管理者向け API や公開範囲の権限分離を入れるなら、次の形のほうが自然になる。

- API にはアクセストークンを使う
- route ごとに scope を設定する
- `email` は監査用のユーザーマッピングか、Cognito 側のトークンカスタマイズで取得する

いまはロールが1つしかなく、全員が同じことをできる。切り替えるのは認可モデルを拡張するときでよい。そのときまで保留する。

## 過去バージョンへの切り戻しを機能として出すか

実体は配信中のものと直前まで配信していたものが残るため、切り戻しは KVS を1回書き換えるだけで実装できる。ただし metadata は履歴を持たないので、「どのバージョン番号がどの実体か」を出すなら metadata に履歴を足す必要がある。

出していないのは、必要になるかが分からないためである。誤って上げ直したときに手元のファイルで上げ直せば済むなら、UI を増やす価値がない。運用してみて「戻したい」が実際に出てきたら足す。
